# 方案 B PoC — 调试指南

本指南说明如何在本机真实环境中验证方案 B（SW 逆向 webmail 接口）的可行性。

## 核心假设

方案 B 依赖以下前提：

1. **浏览器已登录目标邮箱网页**（mail.163.com 或 mail.qq.com）
2. **扩展获取 `host_permissions`** 后，可以在 SW 中对目标域执行跨域 fetch
3. **会话 Cookie 随请求携带**，并能在 Service Worker 的跨域 fetch 中生效
4. **目标 webmail 的内部未读接口**（如 163 的 `/js6/s` RPC 网关）在登录态下能返回未读信息

## 使用步骤

### 1. 加载扩展

1. 打开 Edge/Chrome 浏览器
2. 进入 `edge://extensions/` 或 `chrome://extensions/`
3. 开启 **开发者模式**
4. 点击 **加载已解压的扩展程序**
5. 选择 `extension/` 目录

### 2. 登录邮箱

在浏览器中分别登录需要验证的邮箱网页：

- 163：https://mail.163.com/
- QQ：https://mail.qq.com/

确保登录后能正常看到收件箱和未读数。

### 3. 添加账户

1. 右键扩展图标 → 选项，或点击 Popup 中的"打开设置"
2. 选择邮箱提供商
3. 输入邮箱地址（用于标识账户）
4. 点击"添加"

### 4. 验证

#### 方式一：通过 Popup 手动探测

1. 点击扩展图标打开 Popup
2. 切换到"探测"标签页
3. 点击"探测 163"或"探测 QQ"
4. 观察探测结果

#### 方式二：查看调试日志

1. Popup 中切换到"日志"标签页
2. 查看最新的请求/响应日志
3. 日志级别可在设置中调整为 DEBUG 查看最详细信息

#### 方式三：检查浏览器控制台

1. 打开扩展的 Service Worker：
   - 在 `edge://extensions/` 中找到扩展
   - 点击"Service Worker"链接或"检查视图"
2. 在 DevTools Console 中查看日志

### 5. 判断结果

#### 认证验证通过（方案 B 可行）

```
provider-163: INFO 接口 js6_rpc 探测成功: unreadCount=3
```

或响应内容中包含实际的未读数、邮件列表等信息，且没有 `FA_SECURITY`、登录引导等认证拦截特征。

#### 认证验证失败（方案 B 不可行）

```
provider-163: WARN 接口 js6_rpc 被认证层拦截: FA_SECURITY或需登录
```

或响应内容为登录页面 HTML。此时说明 Cookie 未随跨域 fetch 发送，或浏览器阻止了该操作。

## 调试开关

在设置页面中可调整以下参数：

| 设置项 | 说明 |
|--------|------|
| **日志级别** | `DEBUG` 记录所有请求/响应细节；`INFO` 记录关键步骤 |
| **检查间隔** | 定时自动检查的间隔（1~30 分钟） |
| **探测接口** | 选择要启用的探测接口（可按提供商分别勾选） |

## 常见问题

### Q: 探测时提示"FA_SECURITY"是什么？
A: 这是 163 邮箱的安全层拦截，说明请求未被认证。可能是：
1. 浏览器中未登录 mail.163.com
2. Cookie 未随请求携带（可能是 SameSite 属性限制）
3. 触发风控，需要稍后再试

### Q: 日志中显示 HTTP 302 重定向到登录页？
A: 说明服务端识别到请求未携带有效的会话信息，将请求重定向到登录页面。

### Q: 可以在真实邮箱账号上测试吗？
A: 可以，但建议使用测试邮箱，避免频繁请求触发风控。同时注意在真实环境中保持合理检查频率。

### Q: 为什么有些接口显示"未能解析未读数"？
A: 这表示接口返回成功但没有被解析器识别。可能需要调整解析策略，或 webmail 接口已改版。
