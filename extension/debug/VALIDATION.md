# 混合方案 v0.5.0 — 真实环境验证计划

## 背景：为什么需要混合方案

经真实环境验证发现：
1. **内容脚本可以读取真实未读数**（如 163 邮箱 8 封未读）✅
2. **内容脚本可以从页面 URL 提取 sid**（如 `INdDcKKhuxodUgDvjUZVHhzIloQcYmuA`）✅
3. **163/QQ 的 webmail 是 SPA**，sid 由前端 JS 动态生成，SW 静态 fetch 无法获取

因此设计**混合方案**：
- 内容脚本在页面中提取 sid → 缓存
- SW 用缓存 sid + Cookie 调 API → 实现后台独立检查
- 仅需用户偶尔打开邮箱页同步一次会话

### v0.5.0 核心改进（本次修复）

**问题**：163/QQ 都依赖标签页开启才能获取信息。标签页一旦关闭，全量检查和自动检查都会失败。

**根因**：
1. Provider 代码在没有缓存 sid 时直接中止 API 探测
2. 即使无 sid，163 的 API 会话载体是登录 Cookie（非 URL 参数），本可以直接调通
3. sid 缓存 TTL 仅 30 分钟，过期后无标签页可从中提取新 sid → 后台检查全面失败
4. 无自动恢复机制：自动检查（alarm）遇到无 sid 时不会自动开标签恢复会话

**修复**：
1. **163/QQ provider 不再因缺少 sid 直接中止 API 探测**
   - 163：无 sid 时直接用 Cookie 调 API（URL 移除 sid 参数）
   - QQ：无 sid 时也尝试调 API（QQ 部分接口可仅靠 Cookie 工作），被拦截则标记 needsSid
2. **自动恢复机制**：alarm / manual 检查失败时，自动开后台标签提取 sid → 缓存 → 关闭标签 → 重试 API
3. **sid 缓存有效期延长**：30min → 12h

## 验证步骤

### Step 1：加载扩展
1. `edge://extensions/` → 开发者模式
2. 移除旧版扩展 → 重新加载选择 `extension/` 目录
3. 接受新增的 `cookies` / `scripting` / `tabs` 权限

### Step 2：同步会话（获取 sid）
1. 打开 Options 设置页
2. 找到「混合方案 · 会话与探测」卡片
3. 点击 **🔄 同步163会话**
4. 扩展会自动打开 `mail.163.com`（若已登录则直接进入邮箱）
5. 内容脚本在页面加载后自动提取 sid 并缓存

**预期结果**：
- 会话状态卡片显示 **163邮箱 sid ✅**
- 探测结果显示 `sidObtained: true`

### Step 3：验证 SW 独立 API 探测（标签页关闭状态）
1. 关闭 163 邮箱标签页（保留浏览器不关闭）
2. 回到 Options 页 → 点击 **测试**（对应账户）
3. 或在 Popup → 运行全量检查

**预期（v0.5.0 修复后）**：
- **163**：即使无标签页、无缓存 sid，应能通过 Cookie 直接调 API 成功 → `method: "sw-api"`
- **QQ**：若无 sid，自动开后台标签恢复 → 重试 API → 应能成功
- 若 API 和自动恢复都失败 → 提示需要用户手动登录一次

### Step 4：验证自动恢复（关键场景：关闭全部标签页后自动检查）
1. 登录 163 / QQ 邮箱 → 关闭全部邮箱标签页
2. 等定时检查触发（或手动点击「🚀 运行全量检查」）
3. 预期：扩展自动开后台标签 → 提取 sid → 关闭标签 → API 探测成功
4. 不应出现「需要打开邮箱页面」的失败提示

## 常见问题

**Q: 为什么我点击同步后 sid 还是显示 ❌？**
A: 可能原因：① 邮箱未登录；② 页面未加载完成内容脚本未执行。请确认已登录邮箱并等待页面加载完成后再试。

**Q: 关闭标签页后检查还会自动进行吗？**
A: 会。v0.5.0 已实现自动恢复机制：
- 163：直接通过 Cookie 调 API（无需 sid）
- QQ：无 sid 时自动开后台标签恢复 → 重试 API
- 仅在邮箱完全未登录时才需要用户手动打开登录

**Q: sid 有效期多久？**
A: 12 小时（v0.5.0 从 30 分钟延长）。每次打开邮箱页会自动刷新。
