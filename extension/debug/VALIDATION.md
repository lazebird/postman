# v0.8.0 — 真实环境验证计划

## 背景

目标：在「不打开任何标签页」的前提下，后台自动检查获取 163/QQ 邮箱未读数。

### 核心挑战

SW 直接调用 163/QQ 内部 API 获取未读数一直失败，原因不是 Cookie 问题
（Cookie 诊断显示可附带），而是 **API 请求格式未被正确复现**。
163 的 `js6/s` RPC 网关和 QQ 的 `cgi-bin` 接口有复杂的请求格式。

### v0.8.0 解决方案：API 模式捕获与回放

当用户**偶尔打开**邮箱页面时，内容脚本自动捕获页面实际发出的所有 API 请求
（URL/method/headers/body），sid 替换为 `{sid}` 后持久化。标签关闭后，
SW 使用**真实 API 请求格式**进行后台探测。

## 验证步骤

### Step 1：加载扩展
1. `edge://extensions/` → 开发者模式
2. 移除旧版 → 重新加载选择 `extension/` 目录
3. 版本应为 **0.8.0**

### Step 2：打开邮箱页面 → 验证 API 模式捕获
1. 在浏览器中打开并登录 **163邮箱** (`https://mail.163.com/`)
2. 等待页面完全加载（包括左侧文件夹列表显示未读数）
3. 在扩展 Service Worker 控制台检查日志：
   ```
   [service-worker] 已捕获并保存 netease_163 API 请求: POST https://mail.163.com/js6/s?func=...
   ```
4. 在 Popup → 设置标签页中查看：
   - **163 API 模式** 应显示 > 0 条已学习
5. 同样打开并登录 **QQ邮箱**，确认 **QQ API 模式** 也增加

### Step 3：验证后台自动检查（标签全部关闭）
1. **关闭所有 163 / QQ 邮箱标签**
2. 在 Popup → 手动探测 → 运行全量检查
3. 或在 Options 中手动触发单提供商探测

**预期结果**：
- 不应打开任何新标签
- 应使用捕获的真实 API 模式成功获取未读数
- Popup 状态显示账户已授权、有未读数

### Step 4：验证定时自动检查
1. 确认邮箱标签已全部关闭
2. 等待 alarm 触发（默认 5 分钟）
3. 检查 Popup → 状态：badge 应显示未读总和

## 关键日志

- `[api-patterns] 已保存 netease_163 的 API 模式 N 条` — 捕获成功
- `[163:captured_1] 接口 captured_1 探测成功: unreadCount=8` — 回放成功
- `[qq:captured_3] 接口 captured_3 探测成功: unreadCount=7` — QQ 回放成功

## 判定标准

| 结果 | 结论 |
|------|------|
| API 模式捕获成功 + 标签关闭后探测成功 | ✅ v0.8.0 方案成立 |
| API 模式捕获成功但标签关闭后探测失败 | 需分析 SW fetch Cookie 是否真正附带 |
| API 模式未捕获成功 | 内容脚本拦截器可能未生效，检查注入情况 |
