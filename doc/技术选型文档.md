## 1. 需求概述

### 1.1 核心需求

| 需求项 | 描述 |
|--------|------|
| **目标浏览器** | Microsoft Edge（Chromium 内核，兼容 Chrome 扩展） |
| **支持邮箱** | 163（网易）、Gmail（Google）、USTC（中科大）、QQ 邮箱 |
| **核心功能** | 邮件检查、未读计数、新邮件通知、快速跳转到邮件内容 |
| **性能要求** | 低资源消耗 |
| **通知要求** | 及时通知 |
| **兼容性** | 通用/适配/兼容 |

### 1.2 非功能需求

- **低消耗**：扩展空闲时 CPU/内存占用极低
- **及时性**：新邮件到达后 1-5 分钟内通知（非实时推送）
- **兼容性**：Edge 116+（支持 WebSocket 的最低版本）
- **易用性**：用户配置简单，支持多账户

## 2. 技术方案对比

### 2.1 整体架构方案

| 方案 | 描述 | 优点 | 缺点 | 可行性 |
|------|------|------|------|--------|
| **方案 A：纯浏览器端** | 扩展内直接通过 IMAP/POP3 访问邮件服务器 | 无需后端服务器、部署简单 | MV3 不支持原始 TCP Socket，**不可行** | ❌ 不可行 |
| **方案 B：Gmail API + WebSocket 代理** | Gmail 走官方 REST API，163/QQ/USTC 走 WebSocket 代理桥接 IMAP | Gmail 官方支持、可靠；中国邮箱通过代理可行 | 需要后端代理服务器 | ✅ 推荐 |
| **方案 C：统一 IMAP 代理** | 所有邮箱都通过后端 IMAP 代理服务器 | 架构统一、逻辑简单 | 所有请求都经过代理、增加延迟和服务器负担 | ✅ 可行 |
| **方案 D：内容脚本注入** | 注入到邮件网页中，通过 DOM 读取未读数 | 最简单、无需认证配置 | 仅限已登录网页、依赖 DOM 结构易失效、无法快速跳转到具体邮件 | ⚠️ 有限可行 |
| **方案 E：混合方案（推荐）** | Gmail 走 REST API + 中国邮箱走 IMAP 代理 + 内容脚本辅助 | 兼顾可靠性与兼容性 | 架构复杂度较高 | ✅ **最佳** |

## 3. 邮件提供商支持分析

### 3.1 各提供商协议支持对比

| 维度 | **Gmail** | **163/NetEase** | **QQ Mail** | **USTC (中科大)** |
|------|-----------|-----------------|-------------|-------------------|
| **IMAP 服务器** | `imap.gmail.com:993` SSL | `imap.163.com:993` SSL | `imap.qq.com:993` SSL | `mail.ustc.edu.cn:993` SSL |
| **POP3 服务器** | `pop.gmail.com:995` SSL | `pop.163.com:995` SSL | `pop.qq.com:995` SSL | `mail.ustc.edu.cn:995` SSL |
| **SMTP 服务器** | `smtp.gmail.com:465/587` | `smtp.163.com:465/587` | `smtp.qq.com:465/587` | `mail.ustc.edu.cn:465` |
| **REST API** | ✅ Gmail API (完整) | ❌ 个人版无 | ❌ 个人版无 | ❌ 无 |
| **OAuth2** | ✅ **强制 (2025年起)** | ⚠️ 有但需邮件申请 | ❌ 个人版无 | ❌ 无 |
| **认证方式** | OAuth2 (XOAUTH2) | **授权码** (非登录密码) | **16位授权码** (非QQ密码) | **客户端专用密码** (16位) |
| **2FA 要求** | OAuth 已包含 | 需短信验证开启 IMAP | 需短信验证开启 IMAP | **强制 2FA** (2024.6起) |
| **浏览器直连 IMAP** | ❌ MV3 不可行 | ❌ MV3 不可行 | ❌ MV3 不可行 | ❌ MV3 不可行 |

### 3.2 各提供商接入方案

#### Gmail — 推荐方案：Gmail REST API

```
浏览器扩展 → chrome.identity.getAuthToken() → Gmail API (REST)
```

- 使用 `chrome.identity` API 获取 OAuth2 Token
- 通过 `gmail.readonly` scope 读取邮件
- 通过 `gmail.modify` scope 标记已读
- 支持 `q=is:unread` 查询未读邮件
- **无需后端服务器**

关键 Scopes：

| Scope | 权限 | 用途 |
|-------|------|------|
| `gmail.readonly` | 只读邮件 | 检查未读、读取邮件列表 |
| `gmail.modify` | 读、写、删（不含永久删除） | 标记已读、移动邮件 |
| `gmail.send` | 仅发送 | 回复邮件 |

#### 163/NetEase — 推荐方案：IMAP 代理

- 无公开 REST API
- 必须通过 IMAP + 授权码访问
- 需要后端代理服务器桥接

```
扩展 → WebSocket → 代理服务器 → IMAP (imap.163.com:993) → 163 邮件服务器
```

用户配置项：
1. 邮箱地址
2. IMAP 授权码（非登录密码，需在 163 设置中开启 IMAP 并生成）
3. IMAP 服务器地址（默认 `imap.163.com:993`）

#### QQ Mail — 推荐方案：IMAP 代理

- 无公开 REST API（个人版）
- 必须通过 IMAP + 16位授权码访问
- 需要后端代理服务器桥接

```
扩展 → WebSocket → 代理服务器 → IMAP (imap.qq.com:993) → QQ 邮件服务器
```

用户配置项：
1. QQ 邮箱地址（如 `xxxxx@qq.com`）
2. 16位授权码（非 QQ 密码，需在 QQ 邮箱设置中开启 IMAP 并生成）
3. IMAP 服务器地址（默认 `imap.qq.com:993`）

#### USTC — 推荐方案：IMAP 代理

- 无公开 REST API
- 无 OAuth 支持
- 必须通过 IMAP + 客户端专用密码访问
- 自 2024年6月起强制启用二次验证

```
扩展 → WebSocket → 代理服务器 → IMAP (mail.ustc.edu.cn:993) → USTC 邮件服务器
```

用户配置项：
1. USTC 邮箱地址（如 `xxxxx@ustc.edu.cn`）
2. 客户端专用密码（16位，最多生成6个，生成后只显示一次）
3. IMAP 服务器地址（默认 `mail.ustc.edu.cn:993`）

## 4. Manifest V3 约束与解决方案

### 4.1 核心约束总览

| 约束 | 影响 | 解决方案 |
|------|------|---------|
| Service Worker 30秒空闲终止 | 内存状态丢失、无法维持 IMAP 连接 | `chrome.storage.session/local` 持久化状态 |
| 无 DOM 访问 | 无法解析 HTML 邮件内容 | `chrome.offscreen` + `DOMParser` |
| `setInterval` 不可靠 | SW 终止后定时任务失效 | `chrome.alarms` API（最小间隔 1 分钟） |
| 无 `localStorage` | 传统存储不可用 | `chrome.storage.*` 或 IndexedDB |
| 远程代码禁止 | 不能加载外部脚本 | 打包所有依赖到扩展中 |
| 无原始 TCP Socket | 不能直连 IMAP 服务器 | WebSocket 代理桥接 |
| CSP 更严格 | 不允许 `eval`、`unsafe-inline` | 所有脚本打包、禁止动态执行 |

### 4.2 定时任务方案

**推荐**：`chrome.alarms` API

```javascript
// Service Worker 中注册闹钟
chrome.runtime.onInstalled.addListener(() => {
  chrome.alarms.create("check-email", {
    delayInMinutes: 1,
    periodInMinutes: 5  // 每 5 分钟检查一次
  });
});

chrome.alarms.onAlarm.addListener((alarm) => {
  if (alarm.name === "check-email") {
    checkAllAccounts();
  }
});
```

**亚分钟级需求**（如每 30 秒）：使用 `chrome.offscreen` API

```javascript
// 创建离屏文档运行高频定时器
chrome.offscreen.createDocument({
  url: "offscreen.html",
  reasons: [chrome.offscreen.Reason.DOM_SCRAPING],
  justification: "高频邮件状态检查"
});
```

### 4.3 WebSocket 在 Service Worker 中的使用

Chrome 116+ / Edge 116+ 支持在 Service Worker 中使用 WebSocket，但需要：

1. **20 秒心跳**防止连接超时
2. **最小 Chrome 版本声明**：`"minimum_chrome_version": "116"`

```javascript
let ws = null;
let keepAliveInterval = null;

function connectWebSocket(url) {
  ws = new WebSocket(url);
  
  ws.onopen = () => {
    keepAliveInterval = setInterval(() => {
      if (ws && ws.readyState === WebSocket.OPEN) {
        ws.send("ping");
      }
    }, 20000);
  };
  
  ws.onmessage = (event) => {
    handleEmailNotification(JSON.parse(event.data));
  };
  
  ws.onclose = () => {
    clearInterval(keepAliveInterval);
    ws = null;
    // 下次闹钟触发时重连
  };
}
```

### 4.4 状态持久化方案

```javascript
// 存储选择
const StorageKeys = {
  // 会话级（SW 重启后保留，浏览器关闭后清除）
  SESSION: {
    LAST_CHECK_TIME: "lastCheckTime",
    CURRENT_UNREAD_COUNTS: "unreadCounts"
  },
  // 持久级（卸载扩展前保留）
  LOCAL: {
    ACCOUNTS: "accounts",           // 邮箱账户配置
    SETTINGS: "settings",           // 用户偏好设置
    LAST_EMAIL_IDS: "lastEmailIds"  // 上次邮件ID，用于增量比较
  }

```

## 5. 前端技术栈选型

### 5.1 构建工具对比

| 工具 | 说明 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **WXT** | 新一代浏览器扩展框架 | 原生支持 Chrome/Edge/Firefox/Safari；TypeScript 友好；HMR；模块热重载 | 较新，生态不如 Vite 成熟 | ⭐⭐⭐⭐⭐ |
| **Plasmo** | 浏览器扩展开发框架 | React 优先；内置 UI 组件；自动内容脚本 | 偏向 React、绑定较深 | ⭐⭐⭐⭐ |
| **Vite + 手动配置** | 通用构建工具 + 手动写 manifest | 灵活、无框架约束 | 需要手动维护 manifest、多入口配置 | ⭐⭐⭐ |
| **Webpack** | 传统打包工具 | 成熟稳定 | 配置复杂、构建速度慢 | ⭐⭐ |
| **无构建工具** | 原生 JS 直接开发 | 零依赖、包体积最小 | 无法使用现代语法、维护困难 | ⭐ |

**推荐**：**WXT** — 专为浏览器扩展设计，开发体验最佳，原生支持 Edge 构建。

### 5.2 UI 框架对比

| 框架 | 优点 | 缺点 | 包体积影响 | 推荐度 |
|------|------|------|-----------|--------|
| **React 19** | 社区最大、组件生态丰富、WXT 原生支持 | 较重 | ~40KB gzipped | ⭐⭐⭐⭐⭐ |
| **Vue 3** | 轻量、Composition API 优雅 | 扩展开发社区较小 | ~33KB gzipped | ⭐⭐⭐⭐ |
| **Preact** | React API 兼容、极小体积 | 生态较小 | ~3KB gzipped | ⭐⭐⭐⭐ |
| **原生 JS** | 零依赖、最小体积 | 无组件化、开发效率低 | 0 | ⭐⭐⭐ |
| **Svelte** | 编译时优化、无运行时 | 扩展生态较少 | ~2KB gzipped | ⭐⭐⭐ |

**推荐**：**React 19 + TypeScript** — 扩展开发社区最成熟、参考项目最多、WXT 原生支持。

### 5.3 样式方案对比

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **TailwindCSS v4** | 实用优先、包体积小（按需注入）、与现代框架集成好 | 学习曲线、HTML 类名较长 | ⭐⭐⭐⭐⭐ |
| **CSS Modules** | 局部作用域、无运行时 | 需要构建工具支持 | ⭐⭐⭐⭐ |
| **Shadow DOM** | 完全隔离，不受宿主页面样式影响 | 实现复杂、调试困难 | ⭐⭐⭐ |
| **Plain CSS** | 零依赖 | 全局作用域、易冲突 | ⭐⭐ |

**推荐**：**TailwindCSS v4** — 包体积小、开发效率高、与 React/WXT 集成好。

### 5.4 推荐技术栈总结

| 层级 | 选择 | 版本 |
|------|------|------|
| **清单版本** | Manifest V3 | — |
| **构建工具** | WXT + Vite | 最新 |
| **语言** | TypeScript | 5.x |
| **UI 框架** | React | 19.x |

| **测试** | Vitest + Playwright | 最新 |

## 6. 后端架构方案

### 6.1 后端必要性分析

| 邮箱 | 是否需要后端 | 原因 |
|------|-------------|------|
| Gmail | ❌ 不需要 | Gmail API 可从浏览器直接调用 |
| 163/NetEase | ✅ 需要 | 无 REST API，IMAP 需要 TCP 连接 |
| QQ Mail | ✅ 需要 | 无 REST API，IMAP 需要 TCP 连接 |
| USTC | ✅ 需要 | 无 REST API，IMAP 需要 TCP 连接 |

### 6.2 后端技术方案对比

| 方案 | 语言 | IMAP 库 | 优点 | 缺点 | 推荐度 |
|------|------|---------|------|------|--------|
| **Node.js + imapflow** | TypeScript | imapflow | 与前端统一语言、生态丰富 | 非阻塞 I/O 对 IMAP 长连接不友好 | ⭐⭐⭐⭐ |
| **Go + go-imap** | Go | go-imap | 原生并发、单二进制部署 | 需要学习 Go | ⭐⭐⭐⭐⭐ |
| **Python + imaplib3** | Python | imaplib3 | 开发快速、库成熟 | 性能一般、部署稍复杂 | ⭐⭐⭐ |
| **Cloudflare Workers** | JavaScript | cf-imap | 无服务器、自动扩缩容 | 限制较多（CPU 时间、内存） | ⭐⭐ |

**推荐**：**Node.js + imapflow**（与前端统一语言）或 **Go + go-imap**（性能最优）

### 6.4 安全考虑

- **授权码加密存储**：用户的 IMAP 授权码必须加密存储（AES-256）
- **传输加密**：WebSocket 使用 WSS（TLS）
- **认证机制**：扩展与代理服务器之间使用 JWT Token 认证
- **数据隔离**：每个用户的数据完全隔离
- **日志脱敏**：不在日志中记录授权码等敏感信息

### 7.3 数据流设计

#### 新邮件检查流程

```
1. chrome.alarms 触发 (每5分钟)
   ↓
2. Service Worker 被唤醒
   ↓
3. 从 chrome.storage.local 读取账户配置
   ↓
4. 对每个账户并行执行检查：
   ├── Gmail → fetch Gmail API (REST)
   │         → 解析未读邮件列表
   │         → 比较 lastEmailIds
   └── 163/QQ/USTC → WebSocket 连接代理服务器
                     → 发送 IMAP FETCH 命令
                     → 解析未读邮件列表
                     → 比较 lastEmailIds
   ↓
5. 更新 chrome.storage.session (未读计数)
   ↓
6. 更新 chrome.action.setBadgeText (图标徽章)
   ↓
7. 如有新邮件 → chrome.notifications.create (桌面通知)
   ↓
8. 更新 lastEmailIds 到 chrome.storage.local
```

#### 用户打开 Popup 流程

```
1. 用户点击扩展图标
   ↓
2. Popup 加载 React 应用
   ↓
3. 从 chrome.storage.session 读取未读计数
   ↓
4. 显示各账户未读数
   ↓
5. 用户点击某账户
   ↓
6. 发送消息到 Service Worker
   ↓
7. Service Worker 执行实时检查
   ↓
8. 返回邮件列表
   ↓
9. 用户点击某封邮件
   ↓
10. chrome.tabs.create 打开邮件网页
```

## 8. 风险分析

### 8.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 邮件服务商更新网页导致内容脚本失效 | 高 | 中 | 以 REST API/IMAP 为主，内容脚本为辅 |
| 代理服务器被邮件服务商封禁 IP | 中 | 高 | 分布式部署、IP 轮换、遵守速率限制 |
| Gmail API 审查要求（100+ 用户） | 低 | 中 | 初始阶段限制用户数量、提前准备安全评估 |
| Service Worker 被浏览器异常终止 | 低 | 低 | 所有状态持久化到 storage、闹钟自动重试 |
| 163/QQ 邮箱封禁第三方 IMAP | 低 | 高 | 监控连接成功率、及时更新认证方式 |
| USTC 邮件系统更新导致 IMAP 不可用 | 低 | 中 | 保持与 USTC IT 部门沟通、预留降级方案 |

### 8.2 合规风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 隐私政策不合规 | 中 | 高 | 提供完整隐私政策、明确数据处理方式 |
| Edge 商店审核拒绝 | 低 | 中 | 严格遵循 Edge 开发者政策、提前准备审核材料 |
| 授权码泄露 | 低 | 极高 | AES-256 加密存储、传输加密、最小权限原则 |

### 8.3 用户体验风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 授权码配置流程复杂 | 高 | 中 | 详细图文教程、一键复制授权码步骤 |
| 通知不及时 | 中 | 高 | 支持 WebSocket 实时推送、可配置检查频率 |
| 多账户管理混乱 | 低 | 中 | 清晰的 UI 设计、账户分组显示 |
