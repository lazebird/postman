## 1. 需求概述

### 1.1 核心需求

| 需求项 | 描述 |
|--------|------|
| **目标浏览器** | Microsoft Edge（Chromium 内核，兼容 Chrome 扩展） |
| **支持邮箱** | 163（网易）、Gmail（Google）、USTC（中科大）、QQ 邮箱 |
| **核心功能** | 邮件检查、未读计数、新邮件通知、快速跳转到邮件内容 |
| **性能要求** | 低资源消耗 |
| **通知要求** | 及时通知 |
| **兼容性** | 通用/适配/兼容 |

### 1.2 非功能需求

- **低消耗**：扩展空闲时 CPU/内存占用极低
- **及时性**：新邮件到达后 1-5 分钟内通知（非实时推送）
- **兼容性**：Edge 116+（支持 WebSocket 的最低版本）
- **易用性**：用户配置简单，支持多账户

## 2. 技术方案对比

### 2.1 MV3 扩展的技术限制

| 限制 | 原因 | 影响 |
|------|------|------|
| 无原始 TCP Socket | MV3 Service Worker 没有 `chrome.sockets.tcp` API | 无法直连 IMAP 服务器 |
| 无端口绑定能力 | 扩展无法 `listen()` 绑定本地端口 | 无法运行本地 TCP 服务器 |
| SW 30秒空闲终止 | IMAP 长连接无法在 Service Worker 中维持 | 无法维持持久 IMAP 连接 |
| 无 Node.js `net`/`tls` 模块 | 浏览器环境没有底层网络模块 | 无法在扩展内实现 IMAP 客户端 |

**结论**：扩展本身**无法**直接运行 TCP 服务器来桥接 IMAP。必须采用替代方案。

### 2.2 整体架构方案

| 方案 | 描述 | 后台运行 | 需要服务器 | 需要安装额外程序 | 可行性 |
|------|------|---------|-----------|----------------|--------|
| **方案 A：内容脚本注入** | 注入到邮件网页中，通过 DOM 读取未读数 | ❌ 需保持页面打开 | ❌ 不需要 | ❌ 不需要 | ❌ **不满足需求** |
| **方案 B：Native Messaging（V1 推荐）** | 通过 Native Messaging API 与本地辅助程序通信 | ✅ 后台运行 | ❌ 不需要 | ✅ 需要安装辅助程序 | ✅ **V1 推荐** |
| **方案 C：Gmail API + Native Messaging** | Gmail 走官方 REST API + 中国邮箱走 Native Messaging | ✅ 后台运行 | ❌ 不需要 | ✅ 部分需要 | ✅ 最佳 |
| **方案 D：Gmail API + WebSocket 代理** | Gmail 走官方 REST API + 中国邮箱走 WebSocket 代理桥接 IMAP | ✅ 后台运行 | ✅ 需要 | ❌ 不需要 | ❌ 违反设计约束 |
| **方案 E：统一 IMAP 代理** | 所有邮箱都通过后端 IMAP 代理服务器 | ✅ 后台运行 | ✅ 需要 | ❌ 不需要 | ❌ 违反设计约束 |

## 2.5 新增方案：SW 逆向 Webmail 接口（方案 B，V2 探索）

### 2.5.1 方案来源

在方案 C（Native Messaging）与方案 A（内容脚本）之外，用户提出了第三个方向的探索：
**插件内能否实现"完全无感、纯扩展、无需本地程序"的方案？**

经过多轮讨论与可行性探测，提出了**方案 B：Service Worker 直接请求 webmail 内部 HTTP 接口**获取未读信息。

### 2.5.2 核心思路

```
chrome.alarms（每N分钟唤醒 SW）
        │
        ▼
Service Worker 用 host_permissions 对 mail.163.com / mail.qq.com 的
"未读查询 JSON 接口" 直接 fetch(credentials:'include')
        │  ← 自动带上浏览器里已登录的会话 Cookie，无需任何页面
        ▼
拿到未读数 → badge + 桌面通知
```

### 2.5.3 可行性探测结果（2026-07-24）

#### 163 邮箱

- **接口形态**：统一业务网关 `https://mail.163.com/js6/s?func=<模块>:<动作>`
- 实测 `func=mbox:listMessages / mbox:getUnread` 等能路由到统一鉴权网关
- 未登录会话统一返回 `{'code':'FA_SECURITY'}`（安全层拦截，非404）
- **响应头不含 CORS 头**，content-type 为 `application/octet-stream`
- 会话载体为登录 Cookie（非 URL 参数）

#### QQ 邮箱

- **接口形态**：多个 `/cgi-bin/*` 网关（如 `mail_list`、`readdata`）
- 需要 URL `sid` 参数 + `qm_sk` Cookie 双轨鉴权
- 未认证时返回登录引导页（`text/html; charset=GB18030`）
- **响应同样不含 CORS 头**

#### 核心发现

> 两个 webmail 的接口均为**同源调用**，服务端从未开放 CORS。
> 但 MV3 扩展的 `host_permissions` 允许跨域 fetch 并**绕过 CORS 读取响应**。

**可行性取决于一个关键变量**：扩展 SW 中带 `credentials:'include'` 的 fetch，
能否让浏览器把已登录的 webmail 会话 Cookie 随请求跨域送出并生效？

此问题无法通过静态探测回答，必须**真实登录 + 真实扩展环境实测**。

### 2.5.4 与现有方案的对比

| 维度 | 方案B：SW逆向接口 | 方案C：Native Messaging | 方案A：后台标签 |
|------|-----------------|------------------------|---------------|
| 需要本地程序 | ❌ 不需要 | ✅ 需要 | ❌ 不需要 |
| 需要服务器 | ❌ 不需要 | ❌ 不需要 | ❌ 不需要 |
| 需要后台标签 | ❌ 不需要 | ❌ 不需要 | ✅ 需要 |
| 无感程度 | ⭐⭐⭐⭐⭐ 完全无感 | ⭐⭐⭐ 安装期有感 | ⭐⭐ 有可见标签 |
| 稳定性 | ⭐⭐ 接口易变 | ⭐⭐⭐⭐⭐ 标准IMAP | ⭐⭐⭐ DOM依赖 |
| 开发成本 | 中（需逆向接口） | 高（需开发本地程序） | 低 |
| 部署成本 | 低（商店直接分发） | 高（需引导安装） | 低 |

| 风险 | 等级 | 缓解措施 |

### 2.5.6 方案B PoC 目标

> **目标**：搭建一个最小 MV3 扩展骨架，在已登录邮箱的浏览器中实际验证
> "SW 直接 fetch webmail 接口获取未读数"这一核心假设的可行性。

若验证通过 → 方案 B 成为 V1 候选方案（Gmail 走 REST，国内邮箱走 SW 逆向）

### 2.5.7 实测反馈与修复（2026-09-03）

#### 实测结果

在真实登录环境（163 邮箱，实际未读 8 封）中运行 PoC 探测，接口返回：

```xml
<result>
  <code>FA_UNAUTHORIZED</code>
  <messages>
    <message severity="ERROR">No sid parameter!</message>
  </messages>
</result>
```

#### 根因分析

163 的 `js6/s` 统一 RPC 网关要求每次请求携带 **`sid` 会话令牌**（URL 参数形式）。
原 PoC 代码直接访问业务接口（如 `func=mbox:listMessages`），未先获取 sid。

- 网页免登录是因为登录后前端 JS 先从会话初始化步骤获取 sid，并将其注入后续每个 RPC 请求
- `sid` 是**业务会话令牌**，自动携带 Cookie 不能直接生成 sid
- QQ 邮箱同样需要 `sid`（URL 参数）+ `qm_sk` Cookie 双轨鉴权

#### 修复方案（PoC v0.2.0）

**新增流程：会话初始化 → 取 sid → 带 sid 查未读**

```
1. 获取 sid（新增 shared/session.js 会话管理模块）
   ├── 先查 chrome.storage.session 缓存（30分钟TTL）
   ├── 无缓存 → 访问邮箱登录后入口页面
   │   ├── 163: mail.163.com/js6/main.jsp
   │   └── QQ: mail.qq.com/cgi-bin/login?fun=passport
   ├── 从重定向 URL 或页面内容提取 sid
   └── 提取成功 → 缓存 → 继续；失败 → needsAuth=true

2. 使用 sid 调用业务接口
   ├── URL 中附加 &sid=<sid>
   └── POST 请求携带正确 body

3. 解析响应获取未读数
```

**其他同步修复：**
- POST 请求正确携带 body（原代码发送 POST 但无 body）
- 修复 `response.headers` 序列化问题（`Headers` 对象 → 普通 Object）
- QQ 响应正确处理 GB18030 编码
- 会话失效时自动清除缓存 sid

#### 修复后验证要点

1. 在已登录邮箱的浏览器中加载扩展
2. 打开 Options → 会话状态，确认显示"✅ 已登录"
3. 点击 Popup → 探测 163 / 探测 QQ
4. 观察探测结果中的 `session` 字段（是否获取到 sid）和未读数

### 2.5.8 关键架构结论：SW 跨源无法复用登录 Cookie → 转向方案 C（2026-09-03）

#### 实测结果（v0.2.0 修复后仍失败）

即便实现了「会话初始化 → 取 sid」流程，在真实登录环境再次验证仍失败：

```json
"session": { "sidObtained": false, "loggedIn": false,
  "detail": { "entry": "root_entry", "httpStatus": 200,
    "finalUrl": "https://mail.163.com/",
    "responsePreview": "<!doctype html>...(SPA 壳页面)" } }
```

#### 真正的根因（非代码缺陷，而是架构边界）

多轮修复都停留在「如何拿到 sid」这一表层，却忽略了一个前置硬约束：

> **MV3 Service Worker 发起的跨源 fetch 属于第三方上下文。**
> 163/QQ 的登录 Cookie 大多为 `SameSite=Lax`（默认），
> 浏览器**不会**把 Lax Cookie 随 SW 的跨站后台请求一起发送。
> 因此 SW 无论访问哪个入口页，服务端都判定为「未登录」，自然拿不到任何业务 sid。

补充佐证：
- 163 新版网页已是 **JS-SPA**（返回带 serviceWorker 脚本的壳 HTML），sid 由页面 JS 动态生成，**不存在于任何服务端渲染的静态 HTML** 中 → 靠「抓页面 HTML 正则找 sid」这条路从根上就不成立。
- 用户浏览器标签里「免登录可用」是因为那是**第一方页面上下文**，Cookie 天然附带；与 SW 的第三方上下文是两回事。

#### 有效解法：内容脚本 in-origin 探测（方案 C）

内容脚本注入 `mail.163.com` / `mail.qq.com` 后，运行于**页面同源上下文**：
- fetch/读取**不触发 CORS**，且**第一方 Cookie 天然携带**
- sid 可从页面 iframe / URL / window 直接读取
- 可直接读取 DOM 中已渲染的「收件箱(8)」真实未读数

这绕开了「SW 第三方跨域拿不到 Cookie」的死结，是最可靠的国内邮箱路径。

#### 实现（PoC v0.3.0，方案 C）

```
extension/
├── content/probe-content.js       # 内容脚本：页面内读未读数 + 取 sid + 同源 fetch
├── background/service-worker.js   # 调度：查找/自动打开邮箱标签 → 发给内容脚本
├── shared/session-diagnose.js     # Cookie 诊断：用 chrome.cookies 证明 SameSite 结论
└── manifest.json                  # + cookies/scripting 权限 + content_scripts 声明
```

#### Cookie 诊断（用数据证明结论）

Options → 🍪 诊断会话 Cookie，读取目标站登录 Cookie 的 SameSite/Secure 标志：

| conclusion | 含义 |
|-----------|------|
| `SW_CAN_ATTACH_COOKIES` | 存在 SameSite=None 登录 Cookie，SW 理论可复用 |
| `SW_CANNOT_ATTACH_COOKIES` | 登录 Cookie 均为 Lax/Strict，方案 B 不可行 |
| `NO_AUTH_COOKIE_VISIBLE` | 浏览器未登录 / Cookie 被主机隔离 |

#### 后续方向

方案 C 需要邮箱页面保持打开。达成「后台自动提醒」需配合：
1. 用 `chrome.tabs` 保活一个后台邮箱标签（最小化/固定，极低消耗）
2. 定时向内容脚本发探测指令 → 读未读数 → 桌面通知
3. Gmail 仍走 REST API，不受此限制


### 2.5.9 混合方案 v0.4.0：内容脚本提取 sid + SW 独立 API 检查（2026-09-03）

#### 实测新发现：SW 特权上下文可能可附带 Cookie

Cookie 诊断（chrome.cookies + host_permissions 场景）发现：

| 提供商 | 诊断结果 | 说明 |
|--------|---------|------|
| 163 | `SW_CAN_ATTACH_COOKIES` | 存在 SameSite=None 的 Cookie（NTES_P_UTID） |
| QQ | `SW_CAN_ATTACH_COOKIES` | 存在 SameSite=None 的 Cookie |

关键认知修正：**Chrome MV3 扩展声明 host_permissions 后，从 SW 发起的对该源 fetch
属于特权上下文（first-party），SameSite=Lax 的 Cookie 应当被附带。**
之前「SW 第三方跨域带不上 Cookie」的结论过于绝对——实际验证中，SW fetch 163
主页获得了 200 响应（SPA 壳），而非被重定向到登录页，说明 Cookie 可能已被附带。

真正的问题在于：163 webmail 是 SPA，sid 由前端 JS 动态生成，**不在静态 HTML 中**，
因此 SW 直接 fetch 页面无法获取 sid。

#### 混合方案设计

结合两个已验证的事实：
1. **内容脚本可从邮箱页面提取 sid**（真实环境验证通过，如 `INdDcKKhuxodUgDvjUZVHhzIloQcYmuA`）
2. **内容脚本可读取 DOM 真实未读数**（验证通过，8 封未读）

设计混合模式：**内容脚本提取 sid → SW 用 sid + Cookie 独立调 API**

```
┌─ 偶尔打开邮箱页 ─────────────────────────────────────────────┐
│  内容脚本注入 → 提取 sid → 缓存到 chrome.storage.session       │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌─ SW 定期检查（无需页面）─────────────────────────────────────┐
│  chrome.alarms → 读缓存 sid → 带 sid 调 API → 获取未读数      │
│    ├─ API 成功 → badge + 通知                                 │
│    └─ API 失败 → 回退内容脚本 DOM → 仍失败则提示重新同步        │
└──────────────────────────────────────────────────────────────┘
```

#### 实现要点（PoC v0.4.0）

1. **内容脚本（probe-content.js）**
   - 从页面 URL / DOM 提取 sid（`location.href` 中匹配 `sid=xxx`）
   - 直接写入 `chrome.storage.session`（`sid_163` / `sid_qq` 键，30 分钟 TTL）
   - 优先读取页面标题中的未读数（如 `"(8封未读) 网易邮箱6.0版"`）
   - 其次匹配 DOM 中「收件箱(8)」模式

2. **Service Worker（service-worker.js）**
   - 自动缓存内容脚本上报的 sid
   - 定期检查时先尝试「SW API + 缓存 sid」
   - API 失败或 sid 过期 → 回退到内容脚本 DOM 探测
   - 两种方式都不可用 → 返回 needsTab=true 提示用户同步会话

3. **Provider（provider-163.js / provider-qq.js）**

### 2.5.10 授权与未读获取清晰化（v0.4.1，2026-09-03）

针对真实环境反馈「授权和获取不够清晰，仍难读到未读邮件数目」的定位与改进：

#### 根因
163 / QQ 的 webmail 由多层 iframe 组成。内容脚本以 `all_frames` 注入后，
`chrome.tabs.sendMessage` 只返回**第一个**响应的 frame——当落在联系人等辅助
frame（如 `/contacts/call.do`）时，返回 `unreadCount: null`，即使主收件箱
有未读，整条探测也会被判定「读不到未读数」。同时 QQ 的授权 Cookie 诊断
未覆盖 `qm_sk` / `qm_ssum` 等 host-only 子域 Cookie，导致「是否已授权」判定不准。

#### 改进（本版）
1. **内容脚本区分 frame 角色**：标记 `pageType`（inbox / mailbox / aux）与
   `isTopFrame`，主收件箱能读出未读数才判定为可读取；拿到 sid 即视为已授权
   （`authVerified`），并新增 `needsInboxPage` 提示需切到收件箱主页面。
2. **授权与获取状态机**（service-worker `checkAuthStatus`）：
   - `needs_auth`：未登录/无 sid → 提示登录授权
   - `authed`：已授权可正常读取未读数
   - `authed_no_unread`：已授权但落在辅助页 → 提示打开收件箱
3. **QQ Cookie 诊断修正**：经 `chrome.cookies.getAll({ url })` 读取 host-only 的
   `mail.qq.com` 会话 Cookie，并将 `qm_sk` / `qm_ssum` 纳入 auth 识别。
4. **UI 文案统一为「授权 → 获取未读数」两步流程**，按钮与结果提示给出可操作指引
   （Options / Popup），会话状态卡片展示每个提供商的「未授权 / 已授权 / 已读出未读」。

### 2.5.11 硬性约束：自动运行禁止打开新标签页（v0.7.0 起）

#### 用户明确反馈与决策

用户多次、明确、严厉地否决了"自动运行（alarm 定时检查 / 全量检查）打开新标签页"的行为：

> "自动运行时打开新标签页，造成用户感知和困扰，是不可接受的，明令禁止"
> "每次刷新都自动打开标签是不可接受的，严重影响用户的使用感受，只能考虑完全后台隐藏不可见的方案"
> "用户体验是不可妥协的，必须寻找符合要求的方案，进行接口优化或其他方案探索"

**决策**：此规则已固化至仓库根目录 `AGENTS.md`，为项目最高优先级约束之一。
任何代码修改不得违反此约束。

#### 当前代码保护措施

| 保护点 | 代码位置 | 说明 |
|--------|---------|------|
| `isUserInitiated(context)` 判断 | service-worker.js | alarm 自动触发时返回 false |
| alarm 路径不自动开标签 | `checkSingleAccount` | 非用户触发时跳过 `autoRecoverSid` |
| sid 持久化 7 天 | `cacheProviderSid` | `chrome.storage.local` 存储，重启不丢失 |

即使缓存了 sid，SW fetch 163/QQ 内部 API 获取未读数的成功率
在真实环境**未能完全验证通过**。导致标签关闭后定时自动检查可能失败。

### 2.5.12 方案探索：无标签页获取未读数的候选路径

#### 候选 A：优化 SW API 请求格式（优先级最高，需实测）

163 的 js6/s RPC 请求可能不只是 `func=mbox:listMessages&sid=xxx`。
需从真实登录页面的 Network 面板中抓包确认正确的接口路径和参数格式。

**已知线索**：
- 163 的 `mbox:listMessages` 可能需要 `var` body 中的特定参数（type/ver/pageSize/start/folderId 等）
- QQ 的 `mail_list` 可能需额外的 Cookie 或签名参数
- 页面真实请求可能包含 `df`、`from`、`funcid` 等额外参数

**方法**：在浏览器中打开已登录邮箱页，用 DevTools 观察 Network 中刷新未读数的请求，
提取完整的 URL / headers / body，再在 SW 中精确复现。

#### 候选 B：利用简化未读接口

163/QQ 可能提供轻量的未读查询端点（如 `/cgi-bin/readdata?t=unread&sid=xxx`），
而非复杂 body 的 RPC 接口。需抓包确认是否存在类似端点。

#### 候选 C：WebSocket 实时推送

新版 163/QQ webmail 可能通过 WebSocket 推送新邮件事件。
MV3 Service Worker 支持 WebSocket 连接。若确认可行：
- SW 建立 WebSocket 长连接 → 新邮件推送 → 实时更新 badge
- 无需任何标签页，且通知延迟可从分钟级降至秒级
- 需确认 WebSocket 端点的鉴权方式（Cookie/Token）

#### 候选 D：已在 v0.8.0 验证并否决

"自动打开后台标签→读取→自动关闭"造成标签栏闪烁等视觉干扰，
用户明确否决，不可再尝试。

#### 结论与建议

| 方向 | 可行性 | 建议 |
|------|--------|------|
| SW API 精确复现 | 中 | 短期优先，用抓包获取真实请求格式 |
| 简化未读接口 | 中 | 可与 A 并行探索 |
| WebSocket 推送 | 待验证 | 中长期方向，需确认鉴权方式 |
| 保活标签（否决） | ❌ | 不可接受 |

### 4.1 核心约束总览

| 约束 | 影响 | 解决方案 |
|------|------|---------|

### 4.3 WebSocket 在 Service Worker 中的使用

Chrome 116+ / Edge 116+ 支持在 Service Worker 中使用 WebSocket，但需要：

1. **20 秒心跳**防止连接超时
2. **最小 Chrome 版本声明**：`"minimum_chrome_version": "116"`

```javascript
let ws = null;
let keepAliveInterval = null;

function connectWebSocket(url) {
  ws = new WebSocket(url);
  
  ws.onopen = () => {
    keepAliveInterval = setInterval(() => {
      if (ws && ws.readyState === WebSocket.OPEN) {
        ws.send("ping");
      }
    }, 20000);
  };
  
  ws.onmessage = (event) => {
    handleEmailNotification(JSON.parse(event.data));
  };
  
  ws.onclose = () => {
    clearInterval(keepAliveInterval);
    ws = null;
    // 下次闹钟触发时重连
  };
}
```

### 4.4 状态持久化方案

```javascript
// 存储选择
const StorageKeys = {
  // 会话级（SW 重启后保留，浏览器关闭后清除）
  SESSION: {
    LAST_CHECK_TIME: "lastCheckTime",
    CURRENT_UNREAD_COUNTS: "unreadCounts"
  },
  // 持久级（卸载扩展前保留）
  LOCAL: {
    ACCOUNTS: "accounts",           // 邮箱账户配置
    SETTINGS: "settings",           // 用户偏好设置
    LAST_EMAIL_IDS: "lastEmailIds"  // 上次邮件ID，用于增量比较
  }

```


> #### ⚠️ 关于"扩展更新时数据是否丢失"（重要）
>
> Chrome/Edge 扩展的 `chrome.storage` 两个存储区在**扩展更新（update）与浏览器重启**时行为不同：
>
> | 存储区 | 账号配置等用户数据 | 扩展更新时 | 浏览器重启时 |
> |--------|------------------|-----------|------------|
> | `chrome.storage.local` | 建议放这里 | ✅ **保留**（不丢失） | ✅ 保留 |
> | `chrome.storage.session` | 不适合 | ⚠️ **清空** | ⚠️ 清空 |
>
> **落地原则**
> - **账号配置（ACCOUNTS）、用户设置（SETTINGS）、增量比对基线（LAST_EMAIL_IDS）、检查历史** 等用户数据，**一律写入 `chrome.storage.local`**，从而在每次插件更新后不丢失、无需用户重新添加/配置。本项目 PoC 已按此实现（`shared/storage.js`）。
> - **sid 会话令牌、临时未读数、调试日志** 属短期/会话级数据，放入 `chrome.storage.session`。即使扩展更新时被清空，探测流程会自动重新获取 sid，无需用户干预。
> - MV3 的 Service Worker 上下文**没有页面级 `localStorage`**，跨上下文共享用户数据只能使用 `chrome.storage.local`（其持久化语义等价于传统 localStorage，且专为扩展设计）。
> - 正式版如引入账号授权凭据（邮箱授权码等敏感信息），仍存入 `chrome.storage.local`，并建议启用 `"unlimitedStorage"` 权限与加密处理。

## 6. 无服务器架构设计

### 6.1 设计约束

**核心约束**：
1. **不额外部署服务器**
2. **不依赖保持邮件网页打开**，必须支持后台低资源消耗运行

**MV3 限制**：
- 无原始 TCP Socket API → 无法直连 IMAP 服务器
- Service Worker 30秒空闲终止 → 无法维持长连接
- 无端口绑定能力 → 无法运行本地 TCP 服务器

**可行方案**：Native Messaging + 本地辅助程序（Go 二进制）

### 6.3 Native Messaging 工作原理

**通信流程**：

```
1. Service Worker 通过 chrome.alarms 定期触发检查
   ↓
2. 从 chrome.storage.local 读取账户配置
   ↓
3. 对每个中国邮箱账户：
   a. 构造 JSON 消息:
      {
        "action": "checkMail",
        "account": {
          "email": "user@163.com",
          "password": "授权码",
          "server": "imap.163.com",
          "port": 993
        }
      }
   b. chrome.runtime.sendNativeMessage("com.mail.notifier.bridge", message)
   ↓
4. 辅助程序接收消息
   a. 解析 JSON
   b. 建立 IMAP 连接
   c. 执行 FETCH 命令获取未读邮件
   d. 构造响应 JSON:
      {
        "success": true,
        "unreadCount": 3,
        "emails": [
          {"id": "1", "subject": "...", "from": "...", "date": "..."}
        ]
      }
   e. 写入 stdout
   ↓
5. Service Worker 接收响应
   a. 更新 chrome.storage.session
   b. 更新 chrome.action.setBadgeText
   c. 如有新邮件 → chrome.notifications.create
```

### 7.3 数据流设计

#### 邮件检查流程

```
1. chrome.alarms 触发 (每5分钟)
   ↓
2. Service Worker 被唤醒
   ↓
3. 从 chrome.storage.local 读取账户配置
   ↓
4. 对每个账户执行检查：
   ├── Gmail → fetch Gmail API (REST)
   │         → 解析未读邮件列表
   └── 163/QQ/USTC → chrome.runtime.sendNativeMessage()
                     → 辅助程序建立 IMAP 连接
                     → 执行 FETCH 命令
                     → 返回未读邮件列表
   ↓
5. 更新 chrome.storage.session (未读计数)
   ↓
6. 更新 chrome.action.setBadgeText (图标徽章)
   ↓
7. 如有新邮件 → chrome.notifications.create (桌面通知)
```

#### 用户打开 Popup 流程

```
1. 用户点击扩展图标
   ↓
2. Popup 加载 React 应用
   ↓
3. 从 chrome.storage.session 读取未读计数
   ↓
4. 显示各账户未读数
   ↓
5. 用户点击某账户
   ↓
6. 发送消息到 Service Worker
   ↓
7. Service Worker 执行实时检查
   ↓
8. 返回邮件列表
   ↓
9. 用户点击某封邮件
   ↓
10. chrome.tabs.create 打开邮件网页
```

| 风险 | 概率 | 影响 | 缓解措施 |

### 2.5.13 v0.8.0 全面方案：API 模式捕获与回放（2026-09-03）

#### 问题回顾

经过多轮验证，SW 直接调用 163/QQ 内部 API 获取未读数的成功率极低。
核心原因不是 Cookie 无法附带（Cookie 诊断显示可附带），而是 **API 请求格式未被正确复现**。
163 的 `js6/s` RPC 网关和 QQ 的 `cgi-bin` 接口有复杂的请求格式（URL 参数、headers、body 编码），
仅凭静态分析和猜测难以还原。

#### 新方案：API 模式捕获与回放（API Capture & Replay）

**核心思想**：当用户偶尔打开邮箱页面时，内容脚本**拦截并记录**页面实际发出的所有 API 请求
（URL、method、headers、body），将 sid 替换为 `{sid}` 占位符后持久化存储。
当邮箱标签关闭后，SW 使用这些**捕获到的真实 API 模式**进行后台探测——请求格式与实际页面完全一致。

```
┌─ 用户偶尔打开邮箱页 ──────────────────────────────────────────────┐
│  内容脚本运行                                                      │
│    ├─ 从页面 URL/DOM 提取 sid → 缓存 7天 TTL                      │
│    ├─ 注入 main world fetch/XHR 拦截器 → 捕获实际 API 请求        │
│    │   ├─ URL / method / headers / body                           │
│    │   ├─ sid 自动替换为 {sid} 占位符                              │
│    │   └─ 存储至 chrome.storage.local（api_patterns_163/qq）      │
│    └─ 读 DOM 未读数（即时验证）                                    │
└──────────────────────────────────────────────────────────────────┘
                          ↓
┌─ SW 后台定时检查（无页面打开）─────────────────────────────────────┐
│  chrome.alarms → 读缓存 sid + 捕获的 API 模式                      │
│  → 使用真实 API 格式 fetch（credentials: include）                │
│  → 成功获取未读数 → badge + 通知                                   │
│  → 失败则标记「需手动同步」                                        │
└──────────────────────────────────────────────────────────────────┘
```

#### 与之前方案的关键区别

| 维度 | v0.7.0 静态 API | v0.8.0 API Capture |
|------|-----------------|---------------------|
| 请求格式来源 | 猜测 / 静态分析 | **真实页面捕获** |
| 接口 URL 准确性 | 低（未知真实端点） | **高（实际调用）** |
| headers/body 格式 | 猜测 | **精确复现** |
| sid 处理 | 静态拼接 | **自动替换为 {sid} 占位符** |
| 更新后适配 | 需手动更新代码 | **自动学习新接口** |

#### 实现要点

1. **内容脚本 API 拦截器**（probe-content.js）
   - 注入 main world 脚本，patch `window.fetch` 与 `XMLHttpRequest`
   - 捕获与未读/邮箱相关的请求（URL 包含 `mbox`、`mail_list`、`readdata`、`js6/s` 等关键词）
   - 每帧注入一次，顶层 frame 统一上报

2. **API 模式存储**（shared/api-patterns.js）
   - 持久化至 `chrome.storage.local`
   - sid 自动替换为 `{sid}` 占位符，支持 sid 变化后复用
   - 自动去重，最多保留 30 条
   - 捕获时记录页面 URL 中的 sid 以辅助正确替换

3. **Providers 集成**（provider-163.js / provider-qq.js）
   - 探测时优先尝试捕获的真实 API 模式
   - 成功即停止，不再浪费请求

4. **新增 QQ wx.mail.qq.com 接口**
   - 新版 QQ webmail 运行在 `wx.mail.qq.com`
   - Cookie 诊断也覆盖该子域

#### 验证建议

1. 在浏览器打开已登录的 163/QQ 邮箱页面
2. 检查 Console 日志是否显示「已捕获并保存 XXX API 请求」
3. 在 Popup 中查看「API Patterns」部分确认模式已保存
4. **关闭邮箱标签页**
5. 等待 5 分钟 alarm 触发（或手动全量检查）
6. 观察是否能获取未读数（使用捕获的真实 API 模式）

#### 后续改进方向

- 定期自动清理过期的 API 模式
- 结合 webRequest 或 debugger API 在扩展侧捕获更全面的请求
- 通过捕获的响应格式自动识别未读计数字段
