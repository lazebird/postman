# Mail Notifier 扩展商店发布指南（Chrome Web Store / Microsoft Edge Add-ons）

> 面向 **lazebird/postman** 的正式商店发布全流程操作手册。
> 目标平台：**Google Chrome Web Store** 与 **Microsoft Edge Add-ons**（微软商店可直接复用 Chrome 的验证包）。
> 当前清单版本：`extension/manifest.json` → **v1.0.0**（首个商店发布版本，三者已统一）。
> 打包工具：`./scripts/release.sh pack`（bash 一键打包脚本，详见第 2 节）。
> 文档性质：操作流程 + 检查清单，随版本迭代更新。

---

## 0. 发布前置总览

本项目为 **纯前端 MV3 扩展**，无需服务器、无后端依赖，产物即 `extension/` 目录打包后的 zip。
发布到两家商店的大体路径：

| 事项 | Chrome Web Store | Microsoft Edge Add-ons |
|------|:---:|:---:|
| 发布入口 | https://chrome.google.com/webstore/devconsole | https://partner.microsoft.com/dashboard/microsoftedge |
| 开发者注册费 | **一次性 $5** | **免费** |
| 审查时长 | 常 1~3 个工作日 | 常 1~3 个工作日 |
| 产物包 | 自行打包 zip（zip 需含根级 manifest） | 可**直接复用** Chrome 通过审核的 zip |
| OAuth2/Gmail 关联 | 需关联 GCP 项目并完成一致性验证 | 同左 |
| 隐私政策 | 涉及凭据/Cookie 必须提供公开隐私政策 | 同左 |

> ⚠️ **关键提示**：本扩展请求了 `cookies`、`declarativeNetRequest`、`identity` 等**高敏感权限**，
> 且涉及读取邮箱未读、后台直调第三方邮箱接口（含 Gmail OAuth）。此类扩展会触发**更严格的商店审查**，
> 必须准备**公开的隐私政策**与**使用说明**，否则很可能被驳回。详见第 6 节。

## 1. 发布前代码与配置检查

### 1.1 manifest.json 合规性核对

发布前逐项核对 `extension/manifest.json`：

| 字段 | 当前值 | 发布注意事项 |
|------|--------|------|
| `manifest_version` | `3` | ✅ 合规（两家商店均已主推 MV3） |
| `name` | `Mail Notifier` | 商店展示名，需 ≤75 字符；正式发布建议改**更可检索**的名称 |
| `version` | `0.9.x` | 商店不允许重复上传**相同版本**；每次发布前必须递增 |
| `description` | 长句 | 商店列表展示 description（见 4.1 精简建议） |
| `permissions` | `alarms/storage/notifications/tabs/cookies/scripting/declarativeNetRequest/identity` | **敏感权限**，审查重点 |
| `host_permissions` | 163/QQ/USTC/Gmail | 需在商店说明中声明用途 |
| `oauth2` + `identity` | Gmail `gmail.readonly` | 需 GCP OAuth 一致性验证（见 5.1） |

### 1.2 版本号管理

两家商店都**不允许覆盖已存在的版本号**，且重新上传必须升版本。建议：

- 统一由 **manifest.json 的 `version`** 作为唯一事实来源；
- 每次正式发布前手动递增（当前 0.9.x → 0.10.0 / 1.0.0 首个商店版本建议用**干净的新版本**）；
- 同步更新 `package.json` 的 `version` 与 `doc/整体方案与进度.md` 顶部的版本标注，保持三处一致；
- 发布前跑一遍 `scripts/lint.sh`（Prettier + ESLint），确认代码静态审查通过。
发布打包一键完成：`./scripts/release.sh pack`（详见第 2 节）。

### 1.3 敏感权限自查清单（审查风险最高，务必逐条答复）

商店审核会重点盘问以下内容，**建议提前写好答复话术**（见第 6 节商店说明）：

1. **为什么用 `cookies`？** —— 用于将 Cookie 附加到 SW 后台对 webmail 直调，读取未读数；
2. **为什么用 `declarativeNetRequest`？** ——（如用于修正请求头/规避 CSP 限制），需声明规则用途与数量；
3. **为什么用 `identity` + OAuth2？** —— 走 Gmail 官方 REST API 读未读，需完成 GCP OAuth 一致性验证；
4. **为什么用 `tabs`？** —— 仅用于识别用户已打开邮箱标签并复用，**绝不自动开标签**（对齐 AGENTS 规则 1）。

> 若某项用途说不清或可用更小权限替代，发布前先降权，能显著降低被驳回概率。

### 1.4 发布形态：代码是否混淆的决策记录

> 决策记录：**本项目发布产物保持明文，不做代码混淆**。以下为评估结论，供后续复盘参考。

**结论先行**：对本项目而言，混淆**没有必要且弊大于利**，保持明文发布即可。

**一、混淆实际保护不了什么**
- **防不了 sid / OAuth 令牌泄露**：`cookies`、`storage` 里的会话令牌本就是运行时从用户会话取的，不写死在代码里，混淆对此毫无意义；
- **防不了抓包还原逻辑**：扩展的 API 探测/拦截逻辑可被 DevTools/代理抓流量还原，混淆不改变网络可见行为；
- **代码必然可被还原执行**：浏览器最终要执行 JS，任何前端混淆只是增加有心人几小时的还原成本。

**二、本项目「不该混淆 / 没意义」的点**
- `manifest.json` 无法混淆：权限、`host_permissions`、OAuth2 `client_id` 全部明文，商店审查必须能看到；
- Gmail OAuth2 `client_id` 是**公开标识而非密钥**（Google 对 Chrome 扩展根本不发放 Client Secret），混淆它毫无意义；
- 本项目卖点其实是「合规」：发布文档反复强调「纯本地、静默、不开标签」。代码透明可读反而是**加分项**——审查员看得懂才更快过审，也便于社区信任。

**三、混淆在本项目的实际负作用**
- **MV3 CSP 限制**：manifest 采用 `script-src 'self'`，不能使用 `eval`/`new Function`，主流混淆器若依赖此类会被禁用或需放宽 CSP——**放宽 CSP 本身就是安全隐患**，更难过商店审查；
- **审查风险**：Chrome Web Store 对高度混淆代码会要求**源码还原说明**，解释不清易被拒或拉长审核；
- **调试成本**：崩溃排查与后续维护依赖可读代码，混淆后自找麻烦；
- **可靠性风险**：混淆 bug 修复周期长，对高敏感的探测/拦截逻辑影响所有用户。

**四、商店与开源上的考虑**
- Chrome/Edge **均不强制混淆**，大量官方/大厂扩展以明文发布；
- 本项目代码本就在公开仓库（lazebird/postman）中开源，混淆发布版对「防抄」毫无意义——想抄者直接看源码。

**五、真正该做的是「防泄露」而非「防阅读」**
1. 代码内不硬编码任何 sid / cookie / client secret（当前 sid 走 `storage` 缓存，正确）；
2. 对 `api_patterns_*` 捕获数据、Gmail OAuth 流程做好**存储权限最小化**；
3. 防「同名仿冒 / 改包钓鱼」靠**商店侧品牌注册 + 开源说明**，混淆防不了仿冒。

> ⚠️ 若日后因商业考量仍决定混淆：只对 `providers/` 与 `shared/` 的探测/解析逻辑做**轻度、可调试**的压缩混淆，且**不触碰 manifest、popup 入口、OAuth client_id**，不引入 `eval`、不放宽 CSP、能通过 `scripts/lint.sh`，并在 zip 内附还原说明供商店审查。

## 2. 打包产物

### 2.1 一键打包（推荐）

**两家商店均要求**：zip 内 **manifest.json 位于根级**（不能套一层 `extension/` 目录）。
仓库已提供一键发布打包脚本 `scripts/release.sh`（bash + `zip`），自动完成：版本读取 → 必含文件/图标校验 → 版本一致性核对 → 排除 `debug/`、`*.md`、`*.map`、隐藏临时文件 → 生成 manifest 位于根级的 zip → 回读校验结构。

```bash
# 发布前静态审查（Prettier+ESLint，只读不写回）
./scripts/lint.sh --check

# 仅做发布前校验（版本一致性 + 必含文件），不产出 zip
./scripts/release.sh --check

# 校验并打包到 releases/mail-notifier-<version>.zip
./scripts/release.sh pack

# 单独校验已有 zip 结构
./scripts/release.sh --verify releases/mail-notifier-1.0.0.zip
```

> ⚠️ 本脚本打包时依赖系统 `zip` 命令（Linux/macOS 一般自带，Windows 可在 Git Bash 中安装）。
> 若环境无 `zip`，仅 `--check`/`--verify`/`--version` 仍可用（无需 zip）。
>
> 产物输出在仓库根级 `releases/`（该目录不在版本库内，为发布临时产物）。
`releases/` 建议加入 `.gitignore`，避免误提交构建产物。

### 2.2 手动打包（备用，脚本不可用时）

```bash
cd extension
# 排除 .DS_Store、*.map、debug/、*.md，仅保留发布必需文件
zip -r ../releases/mail-notifier-<version>.zip . \
  -x "*.map" -x "*.md" -x "debug/*" -x ".DS_Store" -x "__MACOSX"
```

发布产物校验：
```bash
unzip -l ../releases/mail-notifier-<version>.zip | head -20   # 确认 manifest.json 在根级
```

### 2.3 发布产物目录布局（zip 内）

```
（zip 根级）
├── manifest.json
├── background/
├── content/
├── providers/
├── shared/
├── popup/
└── icons/            # 必须含 16/32/48/128 各尺寸
```

> ⚠️ `debug/` 目录（调试指南）、`*.md` 文档 **不进入商店产物**，仅留在仓库内供开发使用。
> `scripts/release.sh` 已默认排除这些内容。

验证通过后再执行第 2 节打包。

## 4. 发布到 Chrome Web Store

> 入口：https://chrome.google.com/webstore/devconsole （需 Google 账号）

### 4.1 开发者账号注册
1. 打开 DevConsole → 首次进入引导注册开发者；
2. 缴纳**一次性 $5 注册费**（需绑卡）；
3. 完成开发者身份信息（名称、邮箱）。**开发者名称建议与品牌一致**。

### 4.2 上传新扩展
1. DevConsole → **新增项目**；
2. 填写「项目名称」（可临时，正式名在列表页设置）；
3. **上传文件**：选择第 2 节打包的 `mail-notifier-<version>.zip`；
4. 上传后会自动解析并做基础校验，若报错则回到第 2 节排查（多为 manifest/目录层级问题）。

### 4.3 填写商店列表信息（Store listing）

| 字段 | 建议填写内容 |
|------|------|
| 说明（Description） | 精简、准确：多邮箱（163/QQ/USTC/Gmail）未读提醒、桌面通知、快速跳转；强调**纯后台静默检查、不打开标签** |
| 类别 Category | 生产力 / Productivity |
| 语言 Language | 简体中文 + English（可选多语） |
| 图标（128×128） | 使用 `icons/icon-ok-128.png`（有状态图标，择优展示） |
| 截图 Screenshots | 至少 1 张，推荐 1280×800 或 640×400；建议截 Popup 状态页 / 设置页 / 桌面通知效果 |
| 推广图（可选） | 440×280 小图 |
| 隐私权政策 URL | **必须提供公开可访问的隐私政策**（见第 6 节） |

> 商店要求 128×128 图标为方形、无圆角/透明遮罩；本项目 PNG 为 RGBA 方形，需确认主体不贴边。

### 4.4 权限与隐私相关声明
在「隐私权 / Privacy practices」区：
1. 声明会收集/访问的数据类型（邮箱账户名、未读数、Cookie 会话用于本地检查）；
2. **是否将数据传输/出售**：本项目为纯本地处理、无服务器，应勾选**不传输、不出售**；
3. 声明「远程代码」：不使用（全部本地静态资源）✅；
4. 声明权限用途（对应 1.3 话术）。

### 4.5 提交审核
1. 右上「提交以供审核」；
2. 首次提交会走完整人工审查（1~3 工作日常见，敏感权限更久）；
3. 被驳回会收到邮件与原因，按提示修改后重提（重提需**升版本**）；
4. 审核通过后默认为**公开（Public）**。可先发**受限用户/内部测试**做灰度再公开。

### 5.5 Gmail OAuth redirect_uri 白名单注册（⚠️ 首次提交审核前必做）

> 若跳过本节，首次提交商店审核很可能因 `redirect_uri_mismatch` 被驳回。
> 本扩展的 Gmail OAuth 通过 `launchWebAuthFlow` 实现，redirect_uri 动态使用
> `chrome.runtime.id`（见 `extension/shared/gmail-oauth.js`）。**商店版与本地侧载版的
> 扩展 ID 不同**，因此必须在 Google Cloud 的 OAuth 客户端中同时登记商店版对应的 redirect。

#### 5.5.1 为什么必须登记

代码中 redirect URI 形如：
```
https://<当前安装的扩展ID>.chromiumapp.org/
```
- **本地侧载版** → ID 由浏览器根据 manifest 随机/由 `key` 字段派生；
- **商店正式版** → ID 为商店在**首次上传**时分配的 **CRX ID**（无需等审核通过）。

若 Google OAuth 客户端的「已获授权的重定向 URI」未包含商店版的 `https://<CRX_ID>.chromiumapp.org/`，
商店审核或用户首次安装后同步 Gmail 时即会返回 `Error 400: redirect_uri_mismatch`。

#### 5.5.2 Edge Partner Center 的 ID 含义对照

| Partner Center 字段 | 示例 | 是否用于 redirect_uri | 说明 |
|------|------|:---:|------|
| **CRX ID** | `eahfhnjgokdnenglogjgdjajomeodoee` | ✅ **是** | 商店版扩展 ID = `chrome.runtime.id`，**首传即分配** |
| Microsoft Store ID | `0RDCKG9KDXC9` | ❌ 否 | 商店列表的短标识（Store listing URL），非扩展 ID |
| Product ID | `32f7ba8a-ec8e-4420-ae0c-b22714a3a80f` | ❌ 否 | 微软内部 UUID，与运行时扩展 ID 无关 |
| 公钥 | `MIIBIjAN...` | ❌ 否（但可用于 manifest `key` 对齐开发 ID） | 商店签名用公钥 |

> ⚠️ **结论：扩展 ID = CRX ID（32 位小写字母数字）。** 首传上传包后即可在
> Partner Center「扩展标识」页看到，**无需等审核通过**。

#### 5.5.3 在 Google Cloud Console 中登记 redirect_uri

1. 打开 [Google Cloud Console](https://console.cloud.google.com/) → APIs & Services → Credentials；
2. 找到正在使用的 OAuth 2.0 Client ID（对应 `extension/shared/constants.js` 的 `clientId`）；
3. 编辑该凭据 → **已获授权的重定向 URI（Authorized redirect URIs）**；
4. 逐条添加（可同时保留多条）：
   ```
   https://<Edge商店CRX_ID>.chromiumapp.org/
   https://<Chrome商店CRX_ID>.chromiumapp.org/
   https://<本地开发版ID>.chromiumapp.org/   （若有固定 key 则填 key 对应 ID）
   ```
5. **保存** 后等待数十秒到数分钟传播生效，再重新提交商店审核。

#### 5.5.4（可选）manifest 加 `key` 对齐本地开发 ID

若希望本地「加载已解压的扩展程序」也能用商店的同一个 ID（便于提前用正式 redirect 联调）：
1. 在 `extension/manifest.json` 顶层加 `"key": "<Partner Center 公钥>"`；
2. 重新加载扩展后 `chrome.runtime.id` 将与商店 CRX ID 一致；
3. Google Cloud 只需登记该一个 redirect 即可同时覆盖开发与商店版。

> ⚠️ 注意：若同时发布 Chrome 与 Edge 两家商店，两家分配的 CRX ID 通常不同。
> 由于 `manifest.json` 只能含一个 `key`，无法同时对齐两家 —— 建议不加 `key`，
> 将两家商店的 redirect_uri **分别登记**即可（redirect URI 白名单支持多条）。

## 6. 隐私政策与审查资料准备（两家都必需）

本扩展**读取邮箱凭据/Cookie/未读数**，隐私政策是**硬性要求**，缺失必被驳回。

### 6.1 建议的隐私政策要点
1. **收集什么**：仅在用户本机访问对应邮箱（163/QQ/USTC/Gmail）时，读取其 sid/会话与未读状态；
2. **数据去向**：**全部保存在本地** `chrome.storage.local`，**不上传、不共享、不出售**、无第三方服务器；
3. **Gmail 数据**：经官方 REST API 读取未读，遵循 Google API 服务条款；
4. **Cookie**：仅用于向用户已登录的 webmail 发起本地请求，不外传；
5. **删除方式**：卸载扩展即清除本地数据；
6. **联系方式**：开发者可联系邮箱。

### 6.2 托管隐私政策
- 无独立站点时，可直接基于本仓库 `doc/PRIVACY.md`（已按商店要求写好隐私政策全文）托管到 CNB/Pages 或 GitHub Pages，生成**公开可访问 URL**，填入两家商店；
- 隐私政策 URL 需**https、匿名可访问**，不依赖登录态。

### 6.3 结合 AGENTS 规则的可对外表述
对外宣传/商店描述中，建议主动强调：
- ✅ 纯本地处理、无服务器、无第三方收集；
- ✅ 自动检查完全静默，**绝不自动打开标签**（把内部约束转成卖点）；
- ✅ Gmail 走官方 OAuth 只读。

## 7. 版本升级与迭代流程（发布后）

商店不支持覆盖旧版本号，每次更新走「改代码 → 升版本 → 打包 → 上传」循环：

1. 在仓库开发分支改代码，`scripts/lint.sh` 通过；
2. 递增 `manifest.json` 的 `version`（并同步 `package.json` / 方案文档）；
3. 一键打包 `./scripts/release.sh pack`（产物在 `releases/mail-notifier-<version>.zip`，见第 2 节）；
4. Chrome DevConsole：上传新 zip → 更新商店列表（若文案有变）→ 提交审核；
5. Edge 开发者中心：同样上传新 zip → 提交；
6. 审核通过后，在商店「开发者信息」或 release note 中简要描述变更。

> 建议以 Git Tag（如 `v1.0.0`）标记商店发布点，方便回溯对应产物。
