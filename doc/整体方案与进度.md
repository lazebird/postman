# 浏览器邮箱插件 — 整体方案与当前进度

> 本文档是项目**面向当下的整体方案与进度快照**，与《技术选型文档.md》（历史演进与详细选型）配套阅读。
> 更新日期：2026-09-03 ｜ 当前代码版本：**v0.9.3**

---

## 1. 产品与需求

| 维度 | 内容 |
|------|------|
| 形态 | Microsoft Edge / Chrome 浏览器扩展（**MV3**） |
| 目标邮箱 | 163 / QQ / USTC / Gmail |
| 核心功能 | 未读检查、桌面通知、快速跳转邮件、多账户管理 |
| 硬约束 | ① **无服务器** ② **无需保持网页常开** ③ **低资源消耗** ④ **自动运行完全静默** |

---

## 2. 约束边界（最高优先级，不可违反）

见仓库 `AGENTS.md`，核心两条铁律：

1. **规则 1**：自动运行（`chrome.alarms` 定时 / 全量检查 / 任何非用户点击触发路径）**绝对禁止打开新标签页，也禁止"常驻/保活标签"方案**。
   仅用户主动显式触发（Popup / Options 点击）才允许打开邮箱页同步会话。
2. **规则 3**：会话令牌（sid 等）优先用 `chrome.storage.local` 持久化；定时自动检查用「缓存 sid + Cookie 直调 API / API 模式回放」，仅在完全取不到数据时标记"需手动同步"。

> 这条约束直接决定了技术方案取舍：**凡需后台自动打开的方案一律排除**。

---

## 3. 技术方案决策

### 3.1 MV3 的物理边界

MV3 扩展无法直接建立 TCP（无 `chrome.sockets.tcp`、SW 会被终止），而国内邮箱（163/QQ/USTC）只有 IMAP/TCP 通道。因此后台读未读只有几条出口：

| 方案 | 需本地程序 | 需服务器 | 需常驻网页/标签 | 需逆向接口 | 无感度 | 稳定性 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| **A. Native Messaging** | ✅ | ❌ | ❌ | ❌ | 中（安装期有感） | ★★★★★ |
| **B. SW 逆向 webmail HTTP 接口** | ❌ | ❌ | ❌ | ✅ | ★★★★★ | ★★（接口易变） |
| C. 内容脚本 + 保活邮箱标签 | ❌ | ❌ | ✅ | 部分 | ★★ | ★★★ |
| D. 服务器/Pages 代理 IMAP | ❌ | ✅ | ❌ | ❌ | ★★★ | ★★ + 隐私风险 |

### 3.2 取舍结论

- **Gmail**：官方 REST API + OAuth2（`chrome.identity`），纯插件、最稳，无争议。
- **国内邮箱（163/QQ/USTC）**：无标准开放接口。若坚持"纯插件 + 无服务器 + 不保活标签"，唯一路径是 **方案 B（SW 直调逆向 webmail 接口）**。
- **方案 D（Pages/边缘函数）已排除**：静态托管不能跑任意 TCP；即便 Serverless 也要把授权码托管到第三方云，违背"密码不出本地/无服务器"。
- **方案 C 已排除**：需常驻标签，违反 AGENTS 规则 1。
- **方案 A（Native Messaging）为兜底**：技术上最稳（标准 IMAP），但引入本地二进制、安装与分发复杂，用户最初要求避免。**保留为方案 B 验证失败时的回退选项。**

> **最终选型 = 方案 B 为主 + 内容脚本为辅的"混合检查模式"**，Gmail 走 REST 不受影响。

## 4. 当前整体架构：混合检查模式

```
SW 定时唤醒（alarm，每 N 分钟，全程静默、绝不自动开标签）
   │
   ├── ① SW 独立 API 直调（用持久化 sid + Cookie，credentials:'include'）
   │       ├── ✅ 读到未读数 → 更新 badge + 桌面通知
   │       └── ❌ 失败（sid 失效 / 无有效会话）
   │             ├── ② 检测已打开的邮箱标签 → 有则复用内容脚本读未读（不新开）
   │             └── ③ 无可用标签 → 标记「需手动同步」，不打扰用户
   │
   └── ④（学习机制）用户偶尔打开邮箱时，内容脚本提取 sid + 捕获真实 API 格式
          → 持久化（storage.local），供①在无页面时精确回放
```

关键实现文件（`extension/`，MV3）：

| 文件 | 职责 |
|------|------|
| `manifest.json` | MV3；权限 alarms/storage/notifications/tabs/cookies/scripting/declarativeNetRequest；内容脚本 `run_at: document_start` 全 frame 注入 |
| `background/service-worker.js` | 定时调度、混合检查编排、账户管理、消息路由 |
| `content/probe-content.js` | 提取 sid + in-origin 未读探测 + **API 请求捕获拦截器** |
| `providers/provider-163.js` | 163 SW 接口探测（js6/s RPC，带缓存 sid） |
| `providers/provider-qq.js` | QQ SW 接口探测（cgi-bin） |
| `shared/api-patterns.js` | API 模式捕获、归一化、持久化与回放 |
| `shared/debug.js` | 统一四级日志（Console + storage.session，串行化防丢失） |
| `shared/session-diagnose.js` | Cookie / 会话诊断 |
| `background/possibility-tests.js` | "全可能性"后台无标签测试（穷举 Cookie 附加策略） |
| `popup/` `options/` | 状态 / 探测 / 设置 / 统计 / 日志 UI |

> 详细设计、MV3 约束处理、存储分层等见《技术选型文档.md》。

## 5. 关键实验结论（截至当前，已实证）

> 以下为多轮真实登录环境测试得出的**事实**，是判断后续方向与可行性的依据。

### 5.1 Cookie 通道：结论已修正

早期曾判定"纯 SW 跨源 fetch 带不上会话 Cookie（根因 A）"。经 **"全可能性"测试**（穷举 A1–A5 / D1–D2 Cookie 附加策略）后**推翻该结论**：

- **163：SW 后台 fetch（`credentials:'include'` + 缓存 sid）Cookie 能穿透鉴权、到达 RPC 分发层**。
  证据：返回 `FR_INVALID_REQUEST: Invalid method getSessionInfo for module global`，属"已过鉴权才报方法名错误"；若 Cookie 没带上会直接回 `FA_SECURITY`/`FA_UNAUTHORIZED`（仅手动注入 Cookie 的 A4 策略触发）。
  → **163 后台纯 SW 读取在"会话传递"层面是通的**，此前多轮失败主因是**内置 RPC 的 `func` 方法名与 body 属凭空猜测、在真实命名空间不存在**。
- **QQ：尚未测到 Cookie 通道**。内置 `wx.mail.qq.com/cgi-bin/*` 端点在新版 SPA **全部 HTTP 404（已退役）**；`mail.qq.com/cgi-bin/mail_list` 回登录页。比 163 更靠前一层就卡住（真实接口未知）。

### 5.2 API 捕获链路：目前产出为 0（最大堵点）

"打开页面 → 内容脚本学习真实 API → 后台回放"链路**一条模式都未捕获到**（`endpointCount` 恒等于内置默认端点数）。

- 早期根因：拦截器 `run_at: document_idle` 注入太晚，SPA 初始请求已完成；且自动标签存活仅 2~5s，等不到刷新。
- 已修复（PR #31 / v0.9.3）：拦截器提前到 **`document_start`**，DOM 读取做 body 就绪延迟保护。
- **修复后 QQ 仍为 0**：QQ 新版 webmail-app 的列表/未读数据**不走页面内可拦截的 HTTP fetch/XHR**，极可能走 **WebSocket 或更隐蔽通道**——`document_start` 也拦不到非 HTTP 传输。
- 163 捕获链路缺少真实输入，与 5.1 中"只差真实 func/body"同源。

### 5.3 内容脚本 DOM 读取：稳定可靠

- 163 打开标签后 ~2s 内可读 unread（实测 8）；QQ 多 frame 可读（实测 7），多级跳转链路已走通。
- 但受规则 1 限制，**只能用于用户已打开的标签（复用），不能作为自动后台主路径**。
